# โดเมนของระบบฟินิชชิ่ง

เอกสารนี้อธิบาย "ธุรกิจ" ของระบบ — อ่านให้เข้าใจก่อนแก้ logic ใด ๆ
ข้อมูลทั้งหมดในเอกสารนี้ถูกเขียนเป็นโค้ดไว้แล้วที่ [`shared/constants/stations.ts`](../shared/constants/stations.ts) และ [`shared/constants/steps.ts`](../shared/constants/steps.ts) — แก้ที่นั่นที่เดียว

## 5 สถานี (ไม่ใช่สายการผลิตเส้นตรงเดียว)

| สถานี | ชื่อ | Input | Output | ส่งต่อไปที่ |
| --- | --- | --- | --- | --- |
| S1 | เครื่องเคลือบ ขาวผ่อง/PVC | วัตถุดิบตั้งต้น | WIP1 | S2 **หรือ** S4 |
| S2 | เครื่องเคลือบ PVC | WIP1 (จาก S1) | WIP2 | S4 |
| S3 | เครื่องเคลือบสี ปรุลาย | คัดบอร์ด (วัสดุอิสระ) | FG | คลังสินค้า |
| S4 | เครื่องตัด&แพ็ค ออโต้ T-Bar 1 | WIP1 **หรือ** WIP2 | FG | คลังสินค้า |
| S5 | เครื่องตัด&แพ็ค ออโต้ T-Bar 2 | คัดบอร์ด (วัสดุอิสระ) | FG | คลังสินค้า |

- S1 → S2 เป็นสายต่อเนื่อง ส่วน S3, S4, S5 เป็น 3 ไลน์อิสระที่ผลิต FG แยกกัน
- **ห้าม hardcode ว่า S1 ส่งไป S2 เสมอ** — S1 มี 2 ปลายทาง (ดู `allowedNext` ใน `STATIONS`)
- สถานีที่มี `inputSources` มากกว่า 1 (ปัจจุบันคือ S4) ต้องให้ผู้ใช้เลือกแหล่งวัสดุเข้าในขั้นตอนที่ 1

## งาน (job) — ต้องสร้างก่อนเสมอ

ทุกสถานีทำงานเป็น "job" (ใบงาน) ไม่ได้บันทึกลอย ๆ:

```text
เข้าสถานี → หน้างาน (job)
              ├─ กำลังแปรรูป  → เปิดงาน → บันทึกขั้นตอน 1–4 (ซ้ำได้หลายล็อตในงานเดียว) → กด "จบงาน"
              └─ แปรรูปแล้ว   → อ่านอย่างเดียว บันทึกเพิ่มไม่ได้
```

**ฟอร์มสร้างงานแปรรูป** (ตรงกับฟอร์ม "ขั้นตอนการเริ่ม job" ของ AppSheet เดิม):

| ช่อง | รายละเอียด |
| --- | --- |
| วันที่เริ่มทำงาน | ค่าเริ่มต้น = วันนี้ |
| กะ | กะเช้า / กะดึก |
| รายชื่อพนักงานที่ทำงาน | **เลือกได้หลายคน** (อย่างน้อย 1 คน) |
| เครื่อง | รายการเครื่องของสถานีนั้น (`machines` ใน `STATIONS`) |
| ชนิด PVC | เฉพาะสถานีที่มี `pvcTypes` (ตอนนี้คือ S1) — เลือก 1 รายการ มีช่องค้นหา |

กฎของ job:

1. ทุกแถวใน ledger ต้องผูกกับ `jobId` — ไม่มี job = บันทึกไม่ได้ (server ปฏิเสธด้วย HTTP 400)
2. job ปิดด้วยการ **กดปุ่ม "จบงาน"** เท่านั้น ไม่ปิดอัตโนมัติเมื่อจบขั้นตอนที่ 4 (1 job บันทึกได้หลายล็อต)
3. job ที่ปิดแล้วบันทึกเพิ่มไม่ได้ และกดจบซ้ำได้โดยไม่เปลี่ยนเวลาที่ปิดครั้งแรก
4. รหัส job: `JOB-[สถานี]-[YYMMDD]-[ลำดับ 3 หลัก]` เช่น `JOB-S1-260925-001` (ออกเลขฝั่ง server)
5. กะ/เครื่อง/พนักงาน ถูกกำหนดที่ job — ขั้นตอนที่ 2 จึงแสดงค่าพวกนี้เป็นข้อมูลยืนยัน แก้ไม่ได้ ถ้าต้องแก้ให้จบงานแล้วเริ่มงานใหม่

## รูปแบบหน้าทำงาน: กระดาน vs 4 ขั้นตอน

แต่ละสถานีมี `workMode` ใน `STATIONS`:

| โหมด | ใช้ที่ | หน้าตา |
| --- | --- | --- |
| `board` | **S1** | กระดาน "ข้อมูลเข้า (WIP)" / "ข้อมูลออก" แบบเดียวกับระบบคัดบอร์ดเดิม |
| `steps` | S2–S5 | ฟอร์ม 4 ขั้นตอนทีละล็อต |

### กระดานของ S1

```text
สรุปรายการ:  แผ่นเข้า | แผ่นออก | คงค้าง (HD) | ตัดทิ้ง        [ช่องแก้ตัดทิ้ง + อัพเดทข้อมูล]
┌ ข้อมูลเข้า (WIP) ─────────────┐   ┌ ข้อมูลออก ──────────────────┐
│ [สแกนบาร์โค้ด] [กล้อง] [รับเข้า] │   │ [ออกรหัสใหม่ (n รายการค้าง)] │
│ # | บาร์โค้ด | จำนวน | ลบ       │   │ # | LOT | จำนวน | OUT CODE  │
└──────────────────────────────┘   └────────────────────────────┘
```

- สแกนได้หลายใบสะสมใน 1 งาน • บาร์โค้ดซ้ำในงานเดียวกันถูกปฏิเสธ
- ลบแถวได้เฉพาะแถวที่**ยังไม่ได้ออกรหัส** (กันยอดเข้า/ออกเพี้ยน)
- **คงค้าง (HD) = เข้า − ออก − ตัดทิ้ง** — server ปฏิเสธถ้าติดลบ
- ปิดงานแล้วกระดานเป็นอ่านอย่างเดียว

## 4 ขั้นตอน (สถานีที่ workMode = `steps`)

| ขั้น | ชื่อ | สิ่งที่เกิดขึ้น |
| --- | --- | --- |
| 1 | รับวัตถุดิบ/WIP เข้าสถานี | **สแกน TAG WIP จากแผนกคัดบอร์ด** → ระบบถอดรหัสสินค้า/ขนาด/Lot/จำนวนให้ พนักงานตรวจแก้ได้ |
| 2 | บันทึกข้อมูลก่อนผลิต | ยืนยันข้อมูลจากใบงาน (กะ/เครื่อง/พนักงาน) — S3 มีฟอร์มตั้งค่าสีเพิ่ม (ลูกกลิ้ง 3 ชุด ชุดละ 9 ค่า) |
| 3 | ผลิต / แปรรูป | **ออก TAG ใหม่ของฟินิชชิ่ง** (Lot + running ใหม่จาก server), กรอกผลผลิตและ **"แผ่นเสีย"** — S4/S5 บันทึกวัสดุแพ็คเกจจิ้งเพิ่ม |
| 4 | ปิดล็อต | S1/S2 = ส่งต่อสถานีถัดไป • S3/S4/S5 = เซ็นรับ FG เข้าคลัง |

ความแตกต่างรายสถานีถูกคุมด้วย flag ใน `STATIONS` ไม่ใช่ `if (station === 'S3')` กระจายทั่วโค้ด:

| flag | ความหมาย | ปัจจุบันใช้ที่ |
| --- | --- | --- |
| `hasColorSetup` | มีฟอร์มตั้งค่าสีในขั้นตอนที่ 2 | S3 |
| `hasPackaging` | มีฟอร์มวัสดุแพ็คเกจจิ้งในขั้นตอนที่ 3 | S4, S5 |
| `requiresFgSignature` | ขั้นตอนที่ 4 ต้องเซ็นรับเข้าคลัง | S3, S4, S5 |
| `machines` | รายการเครื่องที่เลือกได้ตอนเริ่มงาน | ทุกสถานี (S1 ยืนยันแล้ว, สถานีอื่นยังเป็นค่าตั้งต้น — ดูหัวข้อท้ายไฟล์) |
| `pvcTypes` | ชนิด PVC ที่ต้องเลือกตอนสร้างงาน (ว่าง = ไม่มีช่องนี้) | S1 |
| `workMode` | `board` = กระดานเข้า/ออก, `steps` = ฟอร์ม 4 ขั้นตอน | S1 = board |
| `lotSeries` | ซีรีส์ 2 ตัวใน LOT ที่ออกใหม่ | S1 = `A5` |
| `outItemPrefix` | prefix รหัสสินค้าขาออก | S1 = `BX58` |

## กฎธุรกิจที่ห้ามละเมิด

1. **"ไม่เซ็นรับ = ไม่ถือเป็น FG"** — ปุ่มยืนยันขั้นตอนที่ 4 ของ S3/S4/S5 ถูกล็อกจนกว่าจะมีทั้งลายเซ็นและชื่อผู้รับ
2. **"แผ่นเสีย" ต้องกรอกทุกครั้งก่อนปิดล็อต** แม้เป็น 0 ก็ต้องกดยืนยัน
3. **Ledger เป็น append-only** — ห้าม UPDATE/DELETE ย้อนหลัง ถ้าต้องแก้ให้บันทึกรายการกลับทางเป็นแถวใหม่
4. **ยอดสมดุล**: รับเข้า = ผลิตออก + แผ่นเสีย + คงค้าง — ตรวจทั้งฝั่ง client (เตือน) และ server (ปฏิเสธ)
5. **ทุก endpoint ที่เขียนข้อมูลต้องรับ idempotency key** เพราะมือถือหน้างานอาจส่งซ้ำตอนเน็ตหลุด
6. **ไม่มี job = บันทึกไม่ได้** — ทุกการบันทึกต้องอยู่ภายใต้ job ที่ยังเปิดอยู่

## กะ

มี 2 กะเท่านั้น: **กะเช้า** และ **กะดึก** (ตามคำในระบบ AppSheet เดิม)
เก็บลงฐานข้อมูลเป็นรหัส `MORNING` / `NIGHT` แล้วแสดงผลด้วย `shiftLabel()` จาก [`shared/constants/shifts.ts`](../shared/constants/shifts.ts)

## TAG

### TAG ที่สแกนเข้า (จากแผนกคัดบอร์ด)

บาร์โค้ดกลางของใบ TAG รวม 3 ส่วนไว้ด้วยกัน:

```text
B494-AV0212 : 1.22 x 2.44 m. : L4+++++++076
└ รหัสสินค้า   └ ขนาด           └ Lot + จำนวน (3 หลักท้าย)
```

`parseTagBarcode()` ถอดค่าพวกนี้ให้แบบ best-effort แล้วเติมลงฟอร์มขั้นตอนที่ 1
**ทุกช่องพนักงานแก้ไขได้** เพราะยังไม่ได้ยืนยันรูปแบบบาร์โค้ดจริงกับหน้างาน

บาร์โค้ดอีกแบบที่เจอในระบบคัดบอร์ด (ไม่มีตัวคั่น): `W499-AV0212260924B633076`
= รหัสสินค้า + วันที่(6) + ลำดับ + จำนวน(3) — `parseTagBarcode()` รองรับทั้งสองแบบ

### ของที่ออกใหม่ (ฟินิชชิ่ง)

ถอดรูปแบบจากหน้าจอระบบคัดบอร์ดเดิม:

| ส่วน | ตัวอย่าง | โครงสร้าง |
| --- | --- | --- |
| LOT | `260925A501` | `[วันที่ YYMMDD][ซีรีส์ 2 ตัว][ลำดับ 2 หลัก]` |
| OUT CODE | `BX58-AV0212L4+++++++0076` | `[รหัสสินค้าขาออก][Lot ต้นทาง][จำนวน 4 หลัก]` |

- 1 รายการที่สแกนเข้า → **ออกรหัสได้ 1 ใบเท่านั้น** (กดซ้ำได้ใบเดิม ไม่ออกเลขใหม่)
- ลำดับออกจาก **ฝั่ง server** ต่อ 1 ซีรีส์ต่อวัน (unique `[lot, running]` ที่ DB)
- เก็บที่ `issued_tags` พร้อม `wip_entry_id` และ `source_tag_code` (unique ทั้งคู่ — บังคับกฎ 1 เข้า 1 ออก)

⚠️ **ยังไม่ยืนยัน**: ความหมายของ `A5` ใน LOT และ prefix `BX58` ของรหัสสินค้าขาออก
ตั้งค่าไว้ที่ `lotSeries` / `outItemPrefix` ของสถานี และสูตรอยู่ที่ `buildFgLot()` / `buildOutCode()` ใน [`shared/utils/tag.ts`](../shared/utils/tag.ts) — แก้ที่เดียวทั้งระบบเปลี่ยนตาม

## คำศัพท์ที่ต้องใช้ให้ตรง

| ในหน้าจอผู้ใช้ | ในโค้ด |
| --- | --- |
| แผ่นเสีย | `defectQty`, `totalScrap` |
| TAG | `tagCode` |
| กะเช้า / กะดึก | `shift: 'MORNING' | 'NIGHT'` |
| งาน / ใบงาน | `job` |

คำที่ผู้ใช้เห็นต้องเป็นคำเดิมจาก AppSheet เสมอ (เช่น ใช้ "แผ่นเสีย" ไม่ใช่ "Scrap") ส่วนชื่อตัวแปรภายในใช้ภาษาอังกฤษได้ปกติ

## สิ่งที่ยังไม่ยืนยัน (ต้องถามผู้ใช้ก่อนสมมติเอง)

- S5 ใช้ฟอร์มเหมือน S4 ทุกจุดหรือไม่ (ตอนนี้ตั้งค่าไว้เหมือนกัน — `hasPackaging: true`)
- S3 มีสองโหมดจริงหรือไม่ (ส่ง FG ตรง vs ส่งเป็นแผ่นรอแพ็คไปสถานีอื่น) — ตอนนี้รองรับแค่ส่งเข้าคลัง
- เกณฑ์ตัวเลข (Yield เป้า, ของเสียเกินกี่ % ถือว่าผิดปกติ) — ต้องให้หัวหน้ากำหนด ห้าม hardcode เป็นค่าสุดท้าย
- รายชื่อพนักงานยังเป็นรายชื่อตัวอย่างใน `app/constants/employees.ts` รอต่อ API จาก Laravel
- **รายชื่อเครื่องของ S2–S5** ยังเป็นค่าตั้งต้น (มีเฉพาะ S1 ที่ยืนยันจากหน้าจอ AppSheet: เครื่องเคลือบขาวผ่อง / เครื่องลามิเนต / ฟอล์ยบนกันร้อน)
- **รายการชนิด PVC** คัดจากหน้าจอ AppSheet ได้ 14 รายการ (ถึง `WAX`) แต่ในภาพรายการยังเลื่อนต่อได้ — ต้องยืนยันว่าครบหรือไม่ และสถานีอื่นนอกจาก S1 ต้องเลือกชนิด PVC ด้วยหรือเปล่า
- **ความหมายของ `A5` (LOT) และ `BX58` (รหัสสินค้าขาออก)** — ถอดจากหน้าจอระบบเดิม ยังไม่ยืนยัน
- รหัสสินค้าขาออกควรมาจาก**ตารางแม็พสินค้าเข้า→ออก** ตอนนี้เดาจาก prefix ของสถานี
- S1 ยังไม่มีช่อง "เสีย (NG)" บนกระดาน (ตกลงกันว่าเอาแค่ เข้า/ออก/คงค้าง/ตัดทิ้ง) — ต่างจากกฎ "แผ่นเสียต้องกรอกทุกครั้ง" ของสถานีที่ใช้ 4 ขั้นตอน
- **ชื่อสินค้า** ยังต้องพิมพ์เองในขั้นตอนที่ 1 เพราะไม่มีตารางมาสเตอร์สินค้าในระบบ (บาร์โค้ดมีแต่รหัส)
- **หน้าพิมพ์ TAG** ยังไม่ได้ทำ (ตกลงกันว่าเอา flow ข้อมูลก่อน) — ใบ TAG เดิมมีปุ่ม "พิมพ์ TAG" และ "เปลี่ยนสี"
- 1 job ควรจำกัดจำนวนล็อตหรือไม่ และต้องให้หัวหน้าอนุมัติก่อนจบงานหรือไม่
